## 步骤 1：建立全量数据模型

### 定位

- **对应 PRD/技术架构**：技术架构设计 §4 ER 概要
- **目标**：一次性建好 ER 概要中列出的全部 13 张表的 SQLAlchemy ORM 模型（`User`、`UserProfile`、`DigitalHumanConfig`、`Capture`、`Card`、`ReviewLog`、`ConceptNode`、`ConceptEdge`、`ChatSession`、`ChatMessage`、`LearningEvent`、`LearningPath`、`PathMilestone`），`ConceptNode.embedding` 用 pgvector 的 `Vector` 类型；跑通 `alembic revision --autogenerate` + `alembic upgrade head`
- **为什么放在第一步**：Capture/Path 等后续模块都要落库，模型和迁移不先定好，后面 API 写了也跑不起来
- **建表范围决策**：一次性建完 ER 概要里的全部表（包括 M2/M3 才用到的 `ChatSession`/`ReviewLog`/`LearningPath` 等），后续模块直接复用现成表，不用每次都跑 Alembic 增量迁移

### 操作步骤

1. **数据库连接层** — 新建 `backend/app/core/database.py`
   - 用 `create_async_engine` + `async_sessionmaker` 建异步 SQLAlchemy engine/session
   - 定义 `Base(DeclarativeBase)` 声明式基类
   - 定义 `get_db()` 依赖注入函数，供 FastAPI 路由使用

2. **模型基类** — 新建 `backend/app/models/base.py`
   - `UUIDMixin`：UUID 主键，`default=uuid.uuid4`
   - `TimestampMixin`：`created_at`/`updated_at`，用 `server_default=func.now()`

3. **枚举定义** — 新建 `backend/app/models/enums.py`
   - 10 个业务枚举：`Domain`（language/humanities/skill）、`CardType`、`CaptureSourceType`、`CaptureStatus`、`ConceptRelationType`、`ChatSessionStatus`、`ChatMessageRole`、`LearningEventType`、`LearningPathStatus`、`PathMilestoneStatus`

4. **13 张业务表模型**，按 ER 概要的关联关系拆成 8 个文件：
   - `app/models/user.py` — `User`、`UserProfile`（1:1）
   - `app/models/digital_human.py` — `DigitalHumanConfig`（与 User 1:1）
   - `app/models/capture.py` — `Capture`（User 1:N，Capture 1:N ConceptNode）
   - `app/models/concept.py` — `ConceptNode`（`embedding` 字段用 `pgvector.sqlalchemy.Vector(1536)`，对应 `text-embedding-3-small` 输出维度）、`ConceptEdge`（source/target 自关联）
   - `app/models/card.py` — `Card`（FSRS 状态字段：`fsrs_state`/`due_at`/`stability`/`difficulty`/`review_count`/`lapses`，跨领域去重字段：`is_merged`/`merged_from_ids`）、`ReviewLog`
   - `app/models/chat.py` — `ChatSession`、`ChatMessage`
   - `app/models/event.py` — `LearningEvent`（用于 DLE 计算）
   - `app/models/path.py` — `LearningPath`、`PathMilestone`

5. **模型统一导出** — 编写 `backend/app/models/__init__.py`，把全部模型类导入并加进 `__all__`，确保 Alembic 的 autogenerate 能扫描到所有表

6. **初始化 Alembic 环境**
   - 因为 `alembic/versions/` 目录已存在但缺 `alembic.ini`/`env.py`，先临时把 `alembic/` 整体移走再跑 `poetry run alembic init alembic` 生成标准模板，再删除临时备份
   - 改写 `alembic/env.py`：
     - 用 `async_engine_from_config` 替换默认的同步 `engine_from_config`（因为项目用 `asyncpg` 驱动）
     - 用 `config.set_main_option("sqlalchemy.url", get_settings().database_url)` 让迁移直接读取 `.env` 里的 `DATABASE_URL`，不用在 `alembic.ini` 里重复配置
     - 导入 `from app.models import Base`，把 `target_metadata` 指向 `Base.metadata`

7. **生成并应用迁移**
   - 确认 Docker 基础设施（`docker compose ps`）三个服务都是 healthy
   - 跑 `poetry run alembic revision --autogenerate -m "init all models"`，成功检测到全部 13 张表
   - **踩坑**：生成的迁移文件里用了 `pgvector.sqlalchemy.vector.VECTOR(dim=1536)`，但文件顶部没有自动加 `import pgvector.sqlalchemy`（Alembic autogenerate 对第三方类型的已知限制），手动在迁移文件顶部补上这一行 import
   - 跑 `poetry run alembic upgrade head`，迁移成功执行无报错

### 验证结果

- `docker exec lingua-postgres psql -U lingua -d lingua_dev -c "\dt"` — 确认 13 张业务表 + `alembic_version`（迁移版本记录表）全部建好
- `docker exec lingua-postgres psql -U lingua -d lingua_dev -c "\d concept_nodes"` — 确认 `embedding` 字段类型正确落地为 `vector(1536)`，外键约束（`ON DELETE CASCADE`/`SET NULL`）和索引符合设计
- `poetry run python -c "from app.models import Base; from app.main import app; print(len(Base.metadata.tables))"` — 输出 `13`，确认应用能正常导入，无循环引用或语法错误

## 步骤 2：开发 Auth 模块（邮箱密码登录）

### 定位

- **对应技术架构**：技术架构设计 §3.2.1 Auth Module
- **目标**：仅邮箱密码注册/登录（OAuth 留到 P1）；bcrypt 密码哈希；JWT access(15min)+refresh(7d) 签发与刷新；`get_current_user` 依赖注入，供后续所有模块复用
- **为什么紧跟第一步**：几乎所有接口都要 `get_current_user` 依赖，不先做会导致后面模块返工加认证

### 操作步骤

1. **核心安全模块** — 新建 `backend/app/core/security.py`
   - `hash_password`/`verify_password`：直接调用 `bcrypt` 库
   - `TokenType` 枚举（ACCESS/REFRESH）区分 token 类型，防止 refresh token 被当 access token 用
   - `create_access_token`/`create_refresh_token`/`decode_token`：用 `python-jose` 签发和解码 JWT

2. **Pydantic Schemas**
   - `app/schemas/user.py` — `UserRead`（`from_attributes=True` 支持从 ORM 对象直接构建）
   - `app/schemas/auth.py` — `RegisterRequest`/`LoginRequest`（密码长度 8-72，对应 bcrypt 上限）、`AccessTokenResponse`、`AuthResponse`（refresh_token 不出现在响应体里，走 Cookie）

3. **Auth Service** — 新建 `backend/app/services/auth_service.py`
   - `register_user`：查重邮箱 → 建 `User` → `flush()` 拿到 `user.id` → 建关联的 `UserProfile` → `commit`
   - `authenticate_user`：查用户 + 校验密码
   - 自定义异常 `EmailAlreadyRegisteredError`/`InvalidCredentialsError`，在路由层转换成对应 HTTP 状态码

4. **API 依赖** — 新建 `backend/app/api/deps.py`
   - `get_current_user`：用 `OAuth2PasswordBearer` 解析 `Authorization: Bearer` 头，解码 access token 取出 `user_id`，查库返回 `User`，供后续模块用 `Depends(get_current_user)` 复用

5. **Auth 路由** — 新建 `backend/app/api/v1/auth.py`，共 5 个接口：
   - `POST /register`、`POST /login`：签发 access_token（响应体）+ refresh_token（httpOnly Cookie，路径限定 `/api/v1/auth`，`samesite=lax`，按 PRD §3.2.1 规格）
   - `POST /refresh`：从 Cookie 读 refresh_token（`Cookie(alias="refresh_token")`），换发新 access_token
   - `POST /logout`：清除 refresh_token Cookie
   - `GET /me`：需要 `Depends(get_current_user)`，返回当前用户信息

6. **挂载路由** — `app/api/v1/__init__.py` 汇总 `auth_router` 成 `api_router`，在 `app/main.py` 里 `app.include_router(api_router, prefix=settings.api_v1_prefix)`

### 踩坑记录

- `passlib[bcrypt]` 组合在当前 `bcrypt` 5.x 下报错 `module 'bcrypt' has no attribute '__about__'`——这是 `passlib`（自 2020 年起未再维护）与新版 `bcrypt`（移除了 `__about__` 属性）之间的已知不兼容问题
- **解决方案**：不再用 `passlib`，直接调用 `bcrypt.hashpw`/`bcrypt.checkpw`；跑 `poetry remove passlib`（连带移除了作为其 extra 带入的 `bcrypt`），再单独 `poetry add bcrypt` 把 `bcrypt` 加回作为直接依赖

### 验证结果

启动服务后用 `curl` 跑通完整流程：
- `POST /register`（201，返回 access_token + 用户信息，Cookie 里正确写入 httpOnly 的 refresh_token）
- `POST /login`（200）
- `GET /me` 携带 `Authorization: Bearer <access_token>`（200，返回用户信息）
- `POST /refresh` 携带 Cookie（200，换发新 access_token）
- `POST /logout`（204）

异常场景验证：
- 重复邮箱注册 → 409 `该邮箱已注册`
- 错误密码登录 → 401 `邮箱或密码不正确`
- 不带 token 访问 `/me` → 401 `Not authenticated`

测试完成后已清理测试用户数据（`users`/`user_profiles` 表中的测试记录）。

## 步骤 3：开发 Capture 模块（P0-1 内容捕获）

### 定位

- **对应 PRD/技术架构**：PRD §6 P0-1 内容捕获与知识提取 / 技术架构设计 §3.2.2 Capture Module
- **目标**：接收粘贴文本/URL/PDF → 异步提取概念（≥3 个）+ 摘要 → 标注已有知识关联 → 触发记忆卡片生成
- **验收标准**：30s 内返回 ≥3 个概念 + 摘要；pgvector 语义相似度阈值 0.75 标注关联
- **为什么先于 P0-5**：内容捕获是整个学习闭环的入口，且 Path 模块"持续调整"逻辑依赖已有学习数据

### AI 服务选型的重大调整（实测踩坑）

技术架构文档 §1.1 原选型是 `OpenAI GPT-4o / Claude 3.5 Sonnet` + `text-embedding-3-small`，但用户只有第三方中转站（micuapi）的 API，实测后发现原选型不可行，调整如下：

1. **中转站 `vip_2` 分组只提供 GPT-5.x 系列对话模型**（`gpt-5.4`/`gpt-5.5`/`gpt-5.6-sol` 等 8 个），既不提供 embedding 模型，也不提供 claude 模型
   - 实测 `POST /v1/embeddings` + `text-embedding-3-small` → `503 model_not_found`
   - 实测 `POST /v1/messages` + `claude-haiku-4-5-20251001` → `503 No available channel`（分组无 claude）
2. **两个 key 的真实用途区分**：
   - `ANTHROPIC_API_KEY`（从 CCSwitch 客户端截图里拿的 `sk-kuDC...`）直接 API 调用返回 **401 Invalid token**——它是 Claude Code / CCSwitch 客户端专用 token，不能直接用于 API 调用
   - `OPENAI_API_KEY`（`sk-q3w8...`）走 OpenAI 兼容格式（Bearer 认证）才是真正能用的，实测 `POST /v1/chat/completions` + `gpt-5.6-sol` → `200` 成功
3. **最终方案**：LLM 统一走中转站 OpenAI 兼容层（`base_url=https://www.micuapi.ai/v1`，模型 `gpt-5.6-sol`）；**Embedding 功能暂时留空**（可插拔，等接入可用 embedding 渠道再补），因此"标注已有知识关联"这条验收项本轮不启用，不阻塞核心链路（提取概念+摘要+生成卡片）

### 操作步骤

1. **装新依赖**：`poetry add anthropic beautifulsoup4 pypdf`（后 anthropic 未采用，实际用已有的 `openai` 包）

2. **配置扩展** — `.env` / `.env.example` / `app/core/config.py` 增加 `OPENAI_BASE_URL`、`ANTHROPIC_BASE_URL` 字段；`OPENAI_MODEL` 从 `gpt-4o` 改为中转站可用的 `gpt-5.6-sol`

3. **LLM 服务** — 新建 `app/ai/llm.py`
   - 用 `AsyncOpenAI(api_key, base_url)` 对接中转站
   - `extract_concepts`：系统提示词要求返回 `{"summary", "concepts":[{"label","definition"}]}` 严格 JSON
   - `generate_cards`：为单个概念生成 1-2 张记忆卡片
   - `_extract_json_text`：去掉 LLM 可能返回的 ```json 代码块包裹

4. **Embedding 占位服务** — 新建 `app/ai/embedding.py`
   - `EMBEDDING_ENABLED = False`，`embed_text` 返回 `None`；接入可用渠道后只需实现此函数，上层无需改动

5. **内容清洗提取** — 新建 `app/services/content_extractor.py`（对应 Input Handler 子模块）
   - `extract_from_url`：httpx 抓取 + BeautifulSoup 去除 script/style/nav 等标签取正文
   - `extract_from_pdf`：pypdf 逐页提取文本（扫描件无文本时报错）
   - `extract_from_text`：直接清洗
   - 统一 20000 字符截断，控制 token 成本

6. **语义关联搜索** — 新建 `app/services/concept_graph_service.py`
   - `find_related_concepts`：pgvector `cosine_distance < 1 - 0.75` 取 top-5；embedding 为 None / 服务未启用时直接返回空列表（可插拔）

7. **核心流水线** — 新建 `app/services/capture_service.py`
   - `create_capture`：落库 pending 状态记录
   - `process_capture`：独立开 DB 会话（与请求生命周期解耦，供 BackgroundTasks/Celery 复用），执行 `提取概念 → 向量化 → 语义关联 → 存概念节点 → 建关联边 → 生成卡片`，状态机 `pending→processing→completed/failed`，领域→卡片类型映射（language→vocabulary / humanities→concept / skill→technique）

8. **Pydantic Schemas** — 新建 `app/schemas/capture.py`：`CaptureCreateRequest`、`CaptureRead`、`ConceptWithRelations`、`CaptureConceptsResponse`

9. **路由** — 新建 `app/api/v1/capture.py`，4 个接口：
   - `POST /capture`（text/url，JSON 提交）、`POST /capture/pdf`（multipart 上传）→ 均用 `BackgroundTasks` 异步触发 `process_capture`，立即返回 202
   - `GET /capture/{id}`（查处理状态）、`GET /capture/{id}/concepts`（查提取的概念+卡片数）
   - 挂到 `api_router`

### 关于异步方案的取舍

技术架构 §3.2.2 写的是 Celery 异步任务链。本轮 M1 开发阶段先用 FastAPI 的 `BackgroundTasks` 实现（避免 Windows 上 Celery worker 的兼容问题和额外进程），但 `process_capture` 写成独立开会话的函数，后续接 Celery 时可直接复用，无需改业务逻辑。

### 验证结果

端到端跑通：注册 → 提交哲学文本 capture（202，状态 pending）→ 等待后台流水线 → 状态变 completed
- 提取出 **4 个概念**：无知之幕、差别原则、社会规则、社会地位
- 生成 **8 张卡片**（每概念 2 张），front_content 为引导回忆的问题，质量良好
- 摘要准确概括原文

**编码问题排查**：API 响应用 `python -m json.tool` 在 Windows 终端显示为乱码，但直接查库（`SELECT label FROM concept_nodes`）确认中文完全正常——乱码是 Windows 终端 json.tool 的显示编码问题，非数据存储问题。

测试完成后已清理测试数据（cards/concept_nodes/captures/user_profiles/users 中的测试记录）。

### 遗留待办

- **Embedding / 语义关联功能未启用**：等接入可用的 embedding 渠道（官方 OpenAI embedding key 或本地开源模型）后，实现 `app/ai/embedding.py` 的 `embed_text` 并置 `EMBEDDING_ENABLED = True`，即可补齐"标注已有知识关联"验收项
- **Celery 异步化未落地**：当前用 BackgroundTasks，后续按技术架构接 Celery（`app/workers/`）

## 步骤 4：开发 Path 模块（P0-5 学习路径生成）

### 定位

- **对应 PRD/技术架构**：PRD §6 P0-5 基础学习路径生成 / 技术架构设计 §3.2.6 Path Module
- **目标**：新用户 5 分钟引导 → "学习起点"报告 + 建议路径；根据学习数据持续调整推荐
- **四个子模块**：Onboarding Engine（引导）→ Starting Point Analyzer（起点分析）→ Path Generator（路径生成）→ Adaptive Adjuster（自适应调整）
- **复用已有模型**：`LearningPath`（含 `starting_point_report` JSONB 字段）、`PathMilestone`、`UserProfile.onboarding_completed`

### 操作步骤

1. **LLM 能力** — `app/ai/llm.py` 新增 `generate_learning_path`
   - 一次调用同时产出起点报告（`level_summary`/`strengths`/`gaps`/`recommendation`）+ 初始路径（`title` + 4-6 个 milestones）
   - 系统提示词约束返回严格 JSON

2. **Pydantic Schemas** — 新建 `app/schemas/path.py`：`OnboardingQuestion`、`OnboardingCompleteRequest`、`MilestoneRead`、`LearningPathRead`

3. **业务逻辑** — 新建 `app/services/path_service.py`
   - **Onboarding Engine**：`ONBOARDING_QUESTIONS` 固定 5 问（领域/目标/水平/每日时间/动机）
   - `complete_onboarding`：调 LLM 生成 → 落库 `LearningPath` + `PathMilestone`（第一个里程碑设 `CURRENT`，其余 `LOCKED`）→ 把 `UserProfile.onboarding_completed` 置 True
   - `get_current_path`：查用户最新的 active 路径（`selectinload` 预加载 milestones）

4. **路由** — 新建 `app/api/v1/path.py`，3 个接口（对应技术架构 §6.1）：
   - `GET /path/onboarding`（获取引导问题列表）
   - `POST /path/onboarding/complete`（完成引导，生成起点报告 + 路径，201）
   - `GET /path/current`（查当前路径，无路径返回 404）
   - 挂到 `api_router`

### 验证结果

端到端跑通：注册 → `GET /path/onboarding`（200，返回 5 个引导问题）→ `POST /path/onboarding/complete` 提交答案（201）→ 生成"日语 N4 → N3 职场应用突破计划"含 6 个有序里程碑 → `GET /path/current`（200，完整返回起点报告 + 里程碑）

数据库验证：
- `learning_paths`：标题、ACTIVE 状态、`starting_point_report` JSONB（含 strengths/gaps/recommendation）正确落库
- `path_milestones`：6 个里程碑 order_index 有序，第一个 `CURRENT`，其余 `LOCKED`
- `user_profiles.onboarding_completed` 正确置 `t`

异常场景：无路径用户查 `/path/current` → 404 `尚未生成学习路径，请先完成引导`。测试数据已清理。

### 说明

Adaptive Adjuster（根据学习数据持续调整路径）M1 只做基础版——路径生成后为静态。"持续调整"依赖 M2 的复习数据（`ReviewLog`）和学习事件（`LearningEvent`），等 M2 有真实学习数据后再补自适应逻辑。

## 步骤 5：搭建前端框架并对接后端接口

### 定位

- **对应技术架构**：技术架构设计 §5 目录结构
- **目标**：路由（react-router-dom）、页面骨架、API service 层（axios 封装，对接 auth/capture/path 接口）、Zustand stores
- **为什么放在后端之后**：后端接口先跑通验证过，前端对接时才有真实数据结构可依赖，避免接口变更导致前端重写

### 操作步骤（分层结构，对齐技术架构 §5）

1. **类型定义** — 新建 `src/lib/types.ts`
   - 与后端 Pydantic schema 一一对应：`User`/`AuthResponse`/`Capture`/`Concept`/`CaptureConceptsResponse`/`OnboardingQuestion`/`StartingPointReport`/`Milestone`/`LearningPath` 等

2. **认证 Store** — 新建 `src/stores/authStore.ts`
   - Zustand store，`accessToken` 存 localStorage（key `lingua_access_token`），`user` 存内存
   - `setAuth`/`setAccessToken`/`setUser`/`clear`

3. **axios 实例** — 新建 `src/services/http.ts`
   - `baseURL: '/api/v1'`（开发环境经 vite 代理转发到后端 8000），`withCredentials: true`（携带 httpOnly refresh_token cookie）
   - 请求拦截：注入 `Authorization: Bearer <token>`
   - 响应拦截：401 时用 refresh cookie 换新 token 并重试一次（`refreshing` 变量做并发去重，避免同时多个请求触发多次 refresh），失败则清空登录态

4. **API 模块** — 新建 `src/services/api.ts`
   - `authApi`：register/login/logout/me
   - `captureApi`：create（text/url）/uploadPdf（FormData）/getStatus/getConcepts
   - `pathApi`：getOnboarding/completeOnboarding/getCurrent

   - `AuthPage.tsx`：登录/注册切换表单
