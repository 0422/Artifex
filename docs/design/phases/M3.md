## 2. 本次完成的功能

### 2.1 浏览器语音输入（STT）

新增文件：

- `frontend/src/services/browserSpeech.ts`

实现内容：

- 封装标准 `SpeechRecognition` 和 Chrome/Edge 的 `webkitSpeechRecognition`。
- 根据对话场景自动选择识别语言：
  - 日语：`ja-JP`
  - 英语：`en-US`
- 支持识别中间结果，并实时写入输入框。
- 点击麦克风可开始或停止识别。
- 处理麦克风权限拒绝、无录音设备、网络识别失败、浏览器不支持等状态。
- 会话结束、发送消息、组件卸载时自动停止识别，避免麦克风资源残留。

识别结果不会自动发送，而是先进入输入框，由用户确认后再发送。这项设计主要基于以下考虑：

- 外语学习场景中，口音和环境噪声会增加误识别概率。
- 自动发送的错误文本会被 AI 当作真实学习输入，并进一步进入纠错和学习报告。
- 保留确认步骤可以减少错误数据对学习分析的污染。

### 2.2 浏览器语音播放（TTS）

继续在 `browserSpeech.ts` 中使用浏览器 `speechSynthesis`：

- AI 每次返回文本后，先按中、英、日标点拆分成句子队列，再依次朗读。
- 英文支持 `. ! ?`，中文和日文支持 `。！？` 等边界；过短片段会自动合并，长无标点文本也会分段，最多生成 10 个播放片段。
- 优先选择语言匹配且由本机提供的系统音色；没有本地音色时再退回同语言的其他系统音色。
- 当前语速为 `0.95`。
- 提供音量按钮，可开启或关闭 AI 语音。
- 每次朗读都有独立 session id。新回复、关闭语音、组件卸载、会话结束或开始录音时，会取消旧 session 和剩余句子，旧回调不能继续推进队列。
- 每个句子设置安全超时，防止个别浏览器不触发 `onend` 导致队列永久阻塞。
- 保留当前 `SpeechSynthesisUtterance` 引用，避免部分浏览器提前回收播放对象。
- 使用 `SpeechSynthesisUtterance.onboundary` 产生发音边界脉冲，并通过 `requestAnimationFrame` 平滑输出 `mouthLevel`，供数字人嘴型使用。

当前音色并非项目内固定音色，而是由操作系统和浏览器提供，所以不同设备上的声音可能不同。

### 2.3 对话页面语音交互

修改文件：

- `frontend/src/pages/ChatPage.tsx`

新增状态：

- `isListening`：是否正在语音识别。
- `speechOutputEnabled`：AI 自动朗读是否开启。
- `isSpeaking`：AI 是否正在播放语音。
- `mouthLevel`：当前 TTS 边界事件产生并经平滑处理后的嘴型强度。

交互表现：

- 录音时麦克风按钮显示红色脉冲状态。
- 输入框占位文字切换为“正在聆听...”。
- AI 播放时音量按钮显示青色脉冲状态。
- 新回复开始、朗读结束、关闭语音或启动麦克风时，会把嘴型强度复位为 0。
- 不支持语音能力的浏览器会禁用对应按钮并显示提示。
- 原有 WebSocket、纠错、学习报告逻辑保持不变，语音识别得到的文本仍复用 `sendText()`。

当前语音链路为：

```text
用户点击麦克风
        ↓
浏览器 SpeechRecognition
        ↓
识别文本进入输入框
        ↓ 用户确认发送
现有 text_message WebSocket
        ↓
FastAPI → 第三方文本模型
        ↓
AI 文本回复
        ├── 显示在消息列表
        ├── 浏览器 speechSynthesis 朗读
        └── 驱动数字人说话状态
```

## 3. 数字人实现

### 3.1 VRM 渲染组件

新增文件：

- `frontend/src/components/DigitalHumanAvatar.tsx`

采用技术：

- Three.js：WebGL 场景、摄像机、灯光、渲染循环。
- `GLTFLoader`：加载 GLTF/VRM 二进制资源。
- `@pixiv/three-vrm`：解析 VRM 人形骨骼、表情、弹簧骨骼和模型元数据。
- `@pixiv/three-vrm-animation`：解析 `.vrma`，并针对当前 VRM 生成人形动画 `AnimationClip`。
- `ResizeObserver`：根据桌面侧栏或移动端全屏面板尺寸调整画布与镜头。
- `requestAnimationFrame`：持续更新 VRM 动画和渲染。
- `IntersectionObserver` 和 `visibilitychange`：数字人离开视口或页面进入后台时暂停渲染，恢复可见后继续。

主要处理：

- 创建透明 WebGL 画布、半球光、主光和青色轮廓光。
- 加载模型后通过包围盒计算人物高度和中心点；默认缩放为 `54%`，相机对准模型垂直中点，使头顶、脚底和动作幅度都保留空间。
- 支持在画布上使用滚轮缩放、鼠标或触控横向拖动旋转。缩放比例和观察角度写入 `localStorage`，刷新后保留。
- 使用 `VRMUtils` 清理不必要顶点和关节，并兼容 VRM 0.x 朝向。
- 组件销毁或更换模型时释放 WebGL、材质、几何体和动画帧资源。
- 模型加载失败或浏览器无法创建 WebGLRenderer 时显示静态头像降级状态，不让整个对话页面进入 React 错误边界。
- 组件根节点提供 `data-avatar-state`，便于自动化测试可靠等待 `loading / ready / error` 状态。

### 3.2 动作和表情

早期尝试过 FBX 动作重定向和程序化手臂角度，但不同模型的骨架轴向、T Pose/A Pose、骨长和肩部权重差异较大，容易出现胳膊扭曲、下垂姿势异常。当前实现已经改为优先使用与 VRM 人形规范匹配的 VRMA 动作，并移除强制手臂下垂和手臂角度覆盖，让动作文件决定完整姿势。

新增文件：

- `frontend/src/services/vrmaAnimation.ts`

该服务使用 `VRMAnimationLoaderPlugin` 读取 VRMA，再通过 `createVRMAnimationClip(animation, vrm)` 为当前模型生成可播放动画。当前接入 pixiv VRoid Project Motion Pack 的 7 个动作：

| 页面动作 | 资源文件 | 含义 |
| --- | --- | --- |
| 全身展示 | `VRMA_01.vrma` | Show full body |
| 问候 | `VRMA_02.vrma` | Greeting |
| V 手势 | `VRMA_03.vrma` | Peace sign |
| 射击 | `VRMA_04.vrma` | Shoot |
| 旋转 | `VRMA_05.vrma` | Spin |
| 模特姿势 | `VRMA_06.vrma` | Model pose |
| 屈伸 | `VRMA_07.vrma` | Squat |

播放层使用 `THREE.AnimationMixer`，动作切换时进行约 `0.35s` 的淡出/淡入，减少突变。自动模式目前按对话状态选择动作：

- 普通待机：`modelPose`。
- AI 正在朗读：`showcase`。
- 积极反馈、`happy` 状态：`greeting`。
- 用户也可以在数字人设置中手动锁定任一 VRMA 动作。

表情系统仍独立于骨骼动作：

- 随机眨眼：每隔约 2.5～5.5 秒触发一次 `blink`。
- `neutral / relaxed / thinking / happy / sad` 映射到 VRM Expression。
- 表情权重逐帧插值；说话时适当降低情绪表情强度，避免压制嘴型。

动作资源版权归 pixiv Inc.，允许在遵守禁止事项的前提下修改和商用；项目界面保留 `Animation credits to pixiv Inc.'s VRoid Project`，原始使用条款保存在 `frontend/public/animations/vrma/Readme_VRMA_MotionPack_EN.txt` 和日文说明中。

### 3.3 当前口型同步

浏览器 `speechSynthesis` 不提供可直接接入 `AudioContext` 的底层音频流，也不提供完整音素或 viseme 时间轴，但多数 Chromium 浏览器会触发单词或字符级 `onboundary` 事件。

当前实现升级为“发音边界驱动的近似口型”：

- 每次 `onboundary` 事件产生一次嘴型目标脉冲。
- 使用 `requestAnimationFrame` 对脉冲进行快速张嘴、较慢闭嘴的平滑插值。
- `mouthLevel` 映射到 VRM 的 `aa` 表情；说话时降低情绪表情强度，避免表情权重压制嘴型。
- 无边界事件时保留较低的说话基线，兼容事件支持不完整的浏览器。
- 朗读取消、结束、报错或切换到录音时立即复位嘴型。

这比固定正弦波更贴近真实说话节奏，但仍不是基于真实音频 RMS 或音素的精确同步。不同浏览器触发边界事件的密度也可能不同。

## 6. 使用方式

```powershell
docker compose up -d
```

启动后端和前端后，在 Chrome 或 Edge 中打开对话页。

4. 说完后检查输入框中的识别结果。

- AI 回复默认自动朗读。
- 点击音量图标可以关闭或重新开启。

- 桌面端直接显示在右侧。
- 移动端点击顶部人物图标打开。

- 自动动作模式默认使用模特姿势，AI 朗读时使用全身展示，积极反馈时使用问候；也可以手动选择其他动作。
- 点击数字人右上角上传图标，可以选择本地 `.vrm` 文件。
- 自定义模型异常时会显示加载失败降级状态，可恢复默认模型。

浏览器语音识别要求运行在 `localhost` 或 HTTPS 环境，Chrome/Edge 的支持最好。

## 7. 当前技术取舍

### 7.1 为什么先用浏览器 STT/TTS

- 不依赖第三方文本中转站是否实现 OpenAI 音频接口。
- 不增加后端上传、存储、转码和音频供应商成本。
- 可以继续复用已有文本 WebSocket、纠错与报告逻辑。
- 适合快速验证语音学习体验。

代价是浏览器兼容性、识别服务稳定性和音色一致性不够可控。

### 7.2 为什么不直接发送录音二进制到现有 WebSocket

当前 WebSocket 使用 JSON 命令和 Pydantic 判别联合类型，直接混入二进制音频会扩大协议复杂度，并需要处理：

- 音频分片编号、顺序和重传。
- 编码格式与浏览器兼容。
- 会话鉴权和单段录音大小限制。
- STT 超时、取消和错误恢复。
- 音频文件存储与清理。

第一版先把语音识别留在客户端，可以保持服务端合同稳定。

### 7.3 为什么先做模拟口型

浏览器 TTS 不提供底层音频数据。为了先形成完整反馈闭环，本轮使用浏览器可获得的 `onboundary` 发音边界驱动嘴型，优于单纯按播放状态做固定周期动画；等后续拥有真实音频或 viseme 数据后再升级精确同步。

### 7.4 为什么选择 VRM

- 项目已经安装 `@pixiv/three-vrm`。
- VRM 有标准化人形骨骼、表情和元数据。
- 适合日系数字人、虚拟教师和角色养成方向。
- 可以替换模型而不重写大部分动画逻辑。

动作格式进一步选择 VRMA，而不是继续直接使用通用 FBX/BVH，主要原因是：

- VRMA 以 VRM 人形骨骼语义为基础，`createVRMAnimationClip()` 可以针对目标 VRM 建立动画轨道，减少手工骨骼重命名和重定向。
- 之前下载的 FBX 在目标模型上出现肩臂扭曲，根因通常是骨架轴向、参考姿势、骨长和权重不同，并不是简单修改文件路径即可解决。
- VRMA 可以保留动作作者设计的完整姿势，因此当前不再额外写入“手臂自然下垂角度”，避免运行时代码与动画关键帧争夺同一骨骼。
- 通用 FBX/BVH 并非不能使用，但需要引入可靠的 retarget pipeline、骨架映射、T Pose/A Pose 校正和逐动作验收，工程成本明显更高。

### 7.5 从 ai-avatar-bot 借鉴了什么

参考开源项目 `YuriCrystal/ai-avatar-bot` 时，主要借鉴的是数字人交互的职责划分和体验设计，而不是直接复制其代码：

- 把文本生成、语音播放、嘴型和角色动作视为相互协作但可独立替换的模块。
- 采用句子队列降低长回复朗读的阻塞感，并为未来接入流式 LLM/TTS 保留队列边界。
- 使用视线、眨眼、呼吸、说话和思考动作提高角色存在感。
- 在页面不可见时暂停渲染，控制 Three.js 的持续资源消耗。

有一项实现不能直接照搬：组件清理阶段不调用 `renderer.forceContextLoss()`。React StrictMode 在开发环境会执行一次挂载、清理、再挂载，强制丢失上下文会破坏同一个 canvas 的第二次初始化，表现为模型不再渲染。当前仅使用 `renderer.dispose()` 和 `VRMUtils.deepDispose()` 清理资源。

## 8. 当前限制

- Firefox 等浏览器可能不支持 Web Speech 语音识别。
- 浏览器识别可能依赖浏览器厂商的在线服务。
- 当前音色无法保证跨设备一致。
- 浏览器 TTS 没有真实音频流，口型是发音边界驱动的近似动画，不能精确对应音素。
- AI 回复仍是整段返回，不是 token 流式输出。
- TTS 已按句排队播放，但必须等完整 AI 回复到达后才开始；尚未做到 LLM 生成一句、TTS 同步播放一句。
- 当前自定义 VRM 模型不会持久化。
- `DigitalHumanConfig` 数据库模型尚未接入 API 和前端设置。
- `ChatMessage.audio_url` 尚未真正使用。
- 当前默认 `free.vrm` 约 26.8 MB，七个 VRMA 合计约 6.6 MB；弱网和移动网络首次加载仍可能较慢。
- VRoid Hub 模型的使用权取决于作者下载页条款，发布或部署前必须单独完成许可证复核，不能沿用 `aoi.vrm` 的 MIT 说明。
- 当前已经接入七个 VRMA，但动作与对话状态的映射仍较粗：待机、朗读和积极反馈只有固定映射，没有根据语义、句子节奏、纠错严重程度或用户发言状态自动选择动作。
- 动作采用全身 `AnimationClip` 淡入淡出，尚未实现上半身/下半身动画分层、骨骼遮罩、动作排队、一次性动作结束回待机和动作打断优先级。
- 当前观察旋转只处理模型绕 Y 轴转身，没有相机绕轨、垂直观察角和自动回正动画。
- 缩放、旋转和面板宽度保存在浏览器 `localStorage`，尚未跟随账号跨设备同步；当前动作选择只存在于页面状态，刷新后回到自动模式。
- 数字人设置虽然已从遮挡画面的弹窗改为独立侧栏，但模型上传、音色、STT provider、表情强度等配置仍未接入后端。
- 尚未实现摄像头视线跟随、真实碰撞处理和自动 VAD barge-in。

## 9. 后续深化路线

### 9.1 AI 文本流式输出

当前 `generate_chat_turn()` 等待模型返回完整 JSON。要实现流式对话，可以重新设计 WebSocket 事件：

```text
ai_response_start
ai_response_delta
ai_response_end
correction
```

需要注意，当前模型一次返回 `reply + correction` 的结构化 JSON。直接流式输出 JSON 不利于前端即时展示。建议拆成两段：

1. 对话回复使用流式纯文本或可增量解析结构。
2. 回复结束后独立生成或解析纠错结果。

前端消息应按 `message_id` 累加 delta，而不是每个 token 新建消息。

### 9.2 流式语音识别

生产版本可以改为：

```text
MediaRecorder / AudioWorklet
        ↓ WebM/Opus 或 PCM 分片
后端 STT 网关
        ↓
独立供应商或自建 faster-whisper
        ↓
partial_transcript / final_transcript
```

可增加：

- VAD 语音活动检测。
- 自动检测用户说完。
- 中间转写结果。
- 噪声抑制和回声消除。
- 录音时长、文件大小和并发限制。
- STT provider 抽象，避免绑定单一供应商。

第三方 AI 文本中转站可以继续只负责 LLM，STT 使用另一套服务。

### 9.3 独立 TTS 服务

可选方向：

- 自建 MeloTTS。
- 自建 CosyVoice。
- Azure、火山引擎或其他提供稳定音色与时间轴的语音服务。

建议增加后端接口：

```text
POST /api/v1/speech/synthesize
GET  /api/v1/speech/voices
```

服务端需要实现：

- `voice_provider` 适配器。
- `voice_id` 和语言映射。
- 音频缓存与对象存储。
- 文本长度限制。
- 超时、重试和降级到浏览器 TTS。

### 9.4 精确口型同步

有真实音频后，可以分为两个等级：

第一等级，音量驱动：

- 用 `AudioContext + AnalyserNode` 获取实时 RMS/频谱。
- 把音量映射到 `aa` 嘴型开合。
- 比当前固定周期动画更贴合语音节奏。

第二等级，viseme 驱动：

- 使用 TTS 服务返回的音素/viseme 时间轴。
- 映射到 VRM 的 `aa / ih / ou / ee / oh`。
- 使用音频播放时钟调度嘴型关键帧。
- 可以明显提升真人感和语言教学中的发音展示能力。

### 9.5 边说边播和低延迟

当前前端已经具备句子切分、顺序播放和 session 取消机制。当 LLM 支持 delta 后，可以把现有队列的输入端从“完整回复”升级为“增量文本”：

```text
LLM token delta
    ↓ 标点/语义边界切句
TTS 句子队列
    ↓
第一句先播放，后续句继续生成
```

需要处理：

- 增量文本中未完成句子的缓存，以及缩写、小数点等英文误切问题。
- 用户打断时同时取消后端 LLM 生成、前端 TTS session 和数字人口型。
- 避免数字人在上一句未结束时播放下一句。
- 后端断线、重连或模型报错时清空未完成句子。

### 9.6 数字人动作系统

当前已经具备七个 VRMA、`AnimationMixer` 淡入淡出、自动/手动动作选择、随机眨眼、情绪表情和近似口型。下一步不再是“接入一个动作文件”，而是把现有动作组织成真正的状态机：

- 定义 `idle / listening / thinking / speaking / encouraging / correcting / interrupted` 等语义状态。
- 区分循环动作和一次性动作；一次性问候、鼓励动作结束后自动回到待机，而不是无限循环。
- 增加动作优先级和取消规则，例如用户开口时立刻打断 AI 说话动作，严重纠错高于普通开心反馈。
- 使用骨骼遮罩或 Animation Layer，让下半身维持站姿时，上半身可以叠加说话、指示或鼓励手势。
- 根据句子长度、音量、语义标签和纠错严重程度选择动作，并限制连续重复同一动作。
- 加入眼睛注视摄像头、消息区域或当前说话者，在多个目标之间平滑切换。
- 优化随机眨眼、微表情、头发和衣物 SpringBone 参数。
- 使用 VAD 检测用户自然开口，自动停止 AI 语音、动作和后端生成，实现无需点击麦克风的 barge-in。
- 如需继续使用 FBX/BVH 资源，应新增离线 retarget 工具链，把通用动作转换、校正并验收为项目使用的 VRMA，避免浏览器运行时临时猜测骨架映射。

### 9.7 数字人配置持久化

后端已经有 `DigitalHumanConfig`，下一步可补充：

- `GET /api/v1/digital-human/config`
- `PUT /api/v1/digital-human/config`
- VRM 模型上传接口和对象存储。
- 音色列表接口。
- 表情强度、待机动画、自动播放、语速设置。

前端已经具备不遮挡数字人主体的右侧设置栏，并使用 `localStorage` 保存面板宽度、视图缩放和旋转角度。下一步是把这些本地配置与现有设置项按用户持久化：

- `vrm_model_url`
- `voice_provider`
- `voice_id`
- `stt_engine`
- `expression_intensity`
- `idle_animation_enabled`
- `avatar_panel_width`
- `view_scale`
- `view_rotation`
- `preferred_motion`

上传模型时需要校验扩展名、MIME、大小、VRM 元数据、贴图数量和许可证信息，避免恶意或超大模型耗尽客户端资源。

### 9.8 性能优化

- 对 VRM 贴图使用 KTX2/Basis 压缩。
- 减少材质、骨骼和 BlendShape 数量。
- 模型加载后缓存到浏览器 Cache Storage 或 IndexedDB。
- 根据设备性能动态调整像素比和动画帧率。
- 当前已在页面隐藏或画布离开视口时暂停渲染；后续可进一步在低电量模式下降低帧率。
- 优先压缩或替换当前约 26.8 MB 的 `free.vrm`，并考虑按需预加载七个 VRMA，避免一次性并发下载全部动作。
- 移动端使用更轻量模型或 LOD。
- 把 Three.js、VRM 和模型资源保持独立延迟加载。

### 9.9 测试与可观测性

建议补充：

- 对 `browserSpeech.ts` 使用 mock SpeechRecognition 做单元测试。
- 测试权限拒绝、无麦克风、识别取消和浏览器不支持。
- WebSocket 流式 delta 顺序、断线和取消测试。
- Playwright 桌面/移动截图测试。
- canvas 非空像素阈值测试。
- VRM 加载失败和超大模型测试。
- VRMA 加载失败、动作缺失、切换淡入淡出和自动状态映射测试。
- 面板分割线边界测试：数字人关闭为 `0px`、宽屏扩展超过旧 `520px` 上限、设置栏打开后仍保留最小对话宽度。
- 模型旋转、缩放、恢复默认值和 `localStorage` 持久化测试。
- 记录 STT 延迟、首 token 延迟、首音频延迟、TTS 时长和播放取消率。

## 10. 推荐实施顺序

建议后续按以下顺序继续：

1. 实现 LLM 文本 delta 流式输出。
2. 把现有浏览器 TTS 句子队列接到 LLM delta，实现第一句生成完成后立即朗读。
3. 接入可获得音频流的 TTS，使用 Web Audio RMS 替换边界近似口型。
4. 使用 VAD 增加自动用户打断，并同时取消 LLM、TTS 和数字人动作。
5. 接入独立 STT 服务，替换浏览器 SpeechRecognition 的兼容性限制。
6. 接入支持 viseme 的 TTS，实现精确口型。
7. 完成 DigitalHumanConfig API、模型上传和用户音色设置。
8. 在现有七个 VRMA 基础上完成语义动作状态机、一次性动作回待机、动作分层、视线和情绪联动。

这条顺序优先降低对话延迟和提升交互闭环，然后再提高数字人的视觉拟真度。
