# M6 世势洞察

> 📌 **2026-10-03 更新**：模块从规划落地为完整实现。原一句话描述（"分板块，利用 AI 追踪工具，每日生成日报和分析"）展开为下文全部内容；~~内容捕获/学习路径/知识图谱~~ 模块已于 2026-10-01 下线，本阶段与它们无依赖。

## 1. 需求背景

知识库管"沉淀的"内容，仪表盘管"回顾的"学习数据，缺一块**向外的窗口**：每天世界上发生了什么值得关注的事。对学英语的用户还有一层额外价值——AI/科技/环境恰是雅思口语 Part 3 的高频话题库。

目标：

- 分板块订阅新闻源（RSS），自动定时抓取；
- LLM 每天把各板块的原始文章策展成**中文日报**（摘要 + 为何值得关注 + 重要度），术语保留英文并附中文注释，服务英语学习；
- 一个「世势洞察」页面读日报，来源可在界面里自管理。

==问题：日报内容用 markdown 存还是结构化 JSON 存？==

```file:2-2 结论：结构化 JSON，不引 markdown 渲染依赖
理由：
1. 前端没有任何 markdown 渲染库（package.json 无 react-markdown/remark），
   为一个展示需求引两个依赖不划算；
2. 日报天然是列表结构（每条 = headline + summary_zh + why_matters + importance
   + url + source_name），结构化后前端能直接渲染「重要度徽章」「外链」，
   markdown 反而要把这些信息硬塞进文本；
3. LLM 侧本来就走 _chat_json 的 JSON 通道，没有额外成本。

代价：summary 只能是纯文本段落，不支持加粗/列表等富文本。可接受。
```

## 5. 实现细节与决策

### 5.1 三张表的拆分

```file:5-1 为什么拆 articles 与 digests 两张表
news_articles = 原始抓取层：一行一个 RSS entry，URL 指纹去重，
                服务「这个链接见过没有」，也是未来的原始流视图素材；
news_digests  = 策展层：一天一板块一行，items JSONB 存 LLM 选中的条目。
                items 里直接嵌 url/source_name，展示层一次读全、免 join。

若只有一张：digest 需要引用 articles 的子集（关联表 or 外键数组），
读一份日报要多一次 join，且 LLM 改写后的 headline 没处放。
```

==问题：三张表要不要带 user_id？==

```file:5-2 结论：不带。全局内容型资源
对比过两种先例：
- EdgeDevice（per-user）：设备是"我的"资产；
- KnowledgeCategory（user_id 可空，空=官方共享）：分类树是"大家的"内容。

新闻源与日报更接近后者——而且是纯内容、无个人数据。
不带的收益：定时任务无需按用户分片；多用户部署时同一份日报自然共享。
代价：以后想支持"每人私有源"要加 user_id nullable 迁移。到那时再说。
```

==问题：枚举成员名与值大小写不一致（AI vs ai）会发生什么？==

```file:5-2b SQLAlchemy Enum 默认按「成员名」读写的坑（2026-10-03 线上踩到）
NewsDomain 成员名是 AI/TECH，值是 ai/tech（前端类型与 seed 都用小写值）。
SQLAlchemy 的 Enum 若不指定 values_callable，读写都按成员名——seed 进去的
是小写 'ai'，ORM 读行时拿 'ai' 按名字查表直接抛：
    LookupError: 'ai' is not among the defined enum values. Enum name: newsdomain
项目里原有枚举（ScenarioLanguage.EN = "EN" 等）名值同形，所以一直没暴露。

修复：models/news.py 用 _news_domain_enum() 工厂统一加
    values_callable=lambda cls: [m.value for m in cls]
迁移文件三处 sa.Enum 同样补上。已建的库无需重跑迁移（列就是 VARCHAR，数据本就是小写）。
| | |
教训：以后定义 Enum，名值保持同形，或第一天就加 values_callable。
```

==问题：schema 的 id 声明成 str 还是 uuid.UUID？==

```file:5-2c Pydantic v2 不会把 UUID lax 转成 str（2026-10-03 线上 500）
news schema 一开始图省事把 id/source_id 声明成 str，ORM 实例给的是
uuid.UUID，model_validate 直接 ValidationError: Input should be a valid
string。房子惯例本来就是 id: uuid.UUID（KnowledgeCategoryRead 就这样），
FastAPI 序列化成 JSON 时自动转字符串，前端收到的仍是 string。
教训：Read 类的 UUID 字段一律 uuid.UUID，别自己转 str。
```

### 5.2 抓取与去重

```file:5-3 fetch_source 单源流程（异常不外抛）
httpx GET（UA 伪装，部分站点 403 默认 python-httpx UA）
  └─ HTTPError → 写 source.last_error，commit，return 0 ← 单源失败不拖垮整批
feedparser 解析
  └─ 无条目 → last_error = "feed 无可解析条目"
逐条：link + title 必备；sha1(规范化 URL) 为指纹
规范化：去掉 utm_*/fbclid/ref/from/spm，小写 scheme+host
        → 同一文章的不同渠道链接算出同一指纹
批次内先去重（feed 自身可能重复给同一链接）
再查库指纹集合，差集 add_all
成功：last_fetched_at = now, last_error = None, commit
```

```file:5-4 整批抓取：每源一个独立子 session
fetch_all_sources 对 enabled 源 asyncio.gather 并发，但【每个源在
async_session_factory() 开的子 session 里跑】。
原因：AsyncSession 不是协程安全的，多协程共用一个 session
execute 会交叉污染事务状态。
单源超时 = news_fetch_timeout_seconds(15s) + 5s 外层兜底。
```

### 5.3 LLM 日报

```file:5-5 提示词设计要点（NEWS_DIGEST_SYSTEM_PROMPT）
1. 这是【筛选】不是【全部点评】：items 允许少于输入，允许为空数组；
2. importance 1-10 判定标准写死：
   9-10 改变行业格局/重大发布/重大政策
   7-8  大厂重要动作/重要研究进展
   5-6  值得了解但影响有限
   1-4  常规更新/小融资/传闻 → 这类不要入选
3. 术语首次出现保留英文附中文注释（LLM（大语言模型））——读者在学英语；
4. url 必须逐字取自输入，严禁编造（防幻觉外链）；
5. 只返回严格 JSON，max_tokens=16000。
   注意：max_tokens 这个参数线上连翻三次车，全靠实测定位——
   ① 3000：reasoning 模型（step-3.7-flash）的 reasoning_content 能吃掉
      7000+ tokens，真实场景 content 直接空返；
   ② 8000：JSON 写一半被截断（finish_reason=length，content 只剩 573 字符）；
   ③ 16000：思考 + 完整 JSON 的双份预算都够，一次通过。
   配套：单板块 LLM 超时 120s → 240s（reasoning 大的日子单次要 1-2 分钟）。
   教训：接 reasoning 模型，max_tokens 按「思考量 × 2 + 输出量」给，别舍不得。
```

```file:5-5b 两个附带的线上修复（2026-10-03 当晚）
1. 六板块并发出限流：generate_all_digests 起初六路全并发，StepFun 对部分
   请求直接空返 → 3/6 降级。加 Semaphore(2) 后全部出稿。
2. LLM 不理会 domain_label：科技/国际/财经板块的 title 全被写成「AI 日报」。
   标题改服务端拼（f"{板块}日报 · {日期}"），不信模型。
3. general 板块出现 items=[] 是正常业务结果：prompt 明确允许「今日无大事」，
   不是 bug。
```

```file:5-6 降级路径（仿 report_service）
LLM 超时/OpenAIError/输出不合法（Pydantic ValidationError）
  → _degraded_content：标题直出 + degraded=True 标记
页面渲染时降级稿显示「降级稿」徽章，用户至少能看到原文标题列表，
而不是空白页。LLM 不可用不影响其他板块（generate_all_digests 里
单板块异常只记日志）。
```

```file:5-7 幂等重生成
upsert 落在唯一约束 (digest_date, domain) 上：
日内重复生成 = 覆盖 items/summary，不新增行。
前端「生成今日日报」连点两次不会产生两份日报。
取材窗口：[当日 0 点 - 36h, min(次日 0 点, now)]，
往前多取 36 小时让昨晚的稿子进次日早报。
```

### 5.4 调度器

```file:5-8 APScheduler 选型留痕（拍板记录）
候选：Celery beat / APScheduler / 手写 asyncio 循环
- Celery：pyproject 里早有 celery[redis]，但从未起过 worker，
  M1 阶段文档明确"为避免 Windows 上 Celery worker 的兼容问题"放弃过；
  为两个定时任务引入两个常驻进程，不划算。
- 手写 asyncio：零依赖，但 misfire/重启补偿/时区都要自己写。
- APScheduler：纯 Python 小依赖，AsyncIOScheduler 直接跑在
  FastAPI 的事件循环里，misfire_grace_time 现成。
结论：APScheduler（拍板 2026-10-03，选项由用户在计划阶段确认）。
```

```file:5-9 两个 job 与 lifespan 接线
fetch job：    IntervalTrigger(minutes=30)，misfire_grace_time=300，max_instances=1
digest job：   CronTrigger(hour=8, minute=3, timezone=固定UTC+8)，
               misfire_grace_time=3600
每个 job 自建 session（async_session_factory），不用请求级 get_db。
main.py lifespan：启动时 start_scheduler()，关闭时 shutdown_scheduler()。
start_scheduler 幂等（_scheduler 单例 + running 检查），
防 uvicorn --reload 重启 worker 时叠加出第二个调度器。
```

==问题：时区为什么用固定 UTC+8 而不是 zoneinfo("Asia/Shanghai")？==

```file:5-10 Windows 上 zoneinfo 的坑
APScheduler 的 CronTrigger 若传 "Asia/Shanghai"，Windows 上
zoneinfo 找不到系统 tz 数据库（Windows 不带），会因缺 tzdata 包
直接抛 ZoneInfoNotFoundError——而部署机在中国，固定偏移量完全够用。
FIXED_TZ = timezone(timedelta(hours=8))，零依赖零坑。
```

## 8. 当前边界

- 日报只有 LLM 策展稿，没有聚类合并（同一事件多源会重复出现）；
- 来源无健康度自动探测，失效只体现在 last_error，需人工替换；
- LLM 成本未做预算控制（每板块每天 1 次，共 6 次/日，建议挂便宜模型）；
- 摘要仅中文，英文原文靠外链；
- 移动端底部导航已自动跟随（6 项），未做单独适配。
