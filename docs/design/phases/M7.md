# M7 摘星阁

> 📌 **2026-10-03 新增模块**：零零散散的语句/想法/备忘录像一颗颗星星，用户站在阁楼上，抓住（点击）哪一颗，就读哪一颗的内容。
>
> 一句话定位：**Artifex 的零摩擦捕获层**。世势洞察给输入、知识库要整理，中间缺一个"先不管，先记下来"的缓冲区——就是这里。
>
> 与已下线的 P0-1「内容捕获」的区别：不做概念提取、不做 LLM 归位、不做知识图谱，只做**捕获 + 重新看见**。

## 1. 需求背景

三个隐喻零件，各自推出设计后果：

```file:1-1 隐喻 → 设计后果
星星   = 单条内容短、碎、无结构；量大；允许一半是废话
         → 不做分类强制、不设必填标签、单条上限 5000 字但 80 字就能成立
阁楼   = 用户是俯视者
         → 夜空 + 阁楼剪影的空间感；位置只由 id 决定，永不重排
抓     = 交互动词是"抓"不是"打开"
         → 抽屉从星体位置 FLIP 飞出；点击零延迟出内容
```

与"待办清单"的根本区别：清单的语义是"欠的"（有清零压力），星星的语义是"落的"（无义务）。因此**没有未读角标、没有待处理计数、没有 streak**——与 PRD 第 8 章 Non-goals 一致。

对标结论（flomo / Keep / Things inbox / Apple 备忘）：捕获层的共识是零 friction 输入 + **被偶然重新看见** + 绝不逼整理。第三条是多数产品做不到的，也是摘星阁唯一的产品差异点。

==问题：抓取之后，星该留在夜空还是被"摘走"？==

```file:2-2 结论：留在夜空，只标记"已抓"
用户原话是"抓一颗星星时就显示该星星代表的内容"——显示是唯一必要动作，
"摘走"是额外脑补。摘走会让语义滑回待办清单（夜空变成"待清空的收件箱"），
且已读内容要跳界面才能再看。

已读反馈用"外圈一道 teal 细环 + 闪烁放缓"实现，零压力。
```

## 5. 实现细节与决策

### 5.1 表结构

==问题：stars 表要不要带 user_id？==

```file:5-1 结论：必带。与 news 三张表不带 user_id 正好相反
news_sources/news_digests 不带 user_id，因为它们是全局内容型资源
（M6.md 5-2）。星星是【最私人的数据】——一个人的念头、没写完的话，
绝不与第二个人共享，也不进任何定时任务。
带 user_id 的代价仅是多一个 where；不带的风险是数据串户。
```

==问题：tags 用 JSONB 数组还是关联表？==

```file:5-2 结论：v1 用 JSONB + GIN 索引，不建 star_tags 关联表
1. 单用户个人标签，量级几十个，永不需要重的按标签聚合查询；
2. PG 的 jsonb @> 走 GIN 索引，与关联表在同一数量级；
3. 省两张表和一个 join，与 news_digests.items 用 JSONB 的既有判断一致
   （M6.md：展示层一次读全，免 join）。

代价：标签不能改名（v1 一并【不做】改名功能）。
升级路径明确：真要标签管理，加 star_tags + star_tag_links + 数据回填迁移。
```

==问题：`origin_ref` 要不要外键？==

```file:5-3 结论：不要。跨模块软引用
硬外键会让"删一篇日报"连带引爆 stars 表，也会把 news→stars 的依赖方向焊死。
Card.source_concept_id 这个硬外键的存废史（随概念图谱整体删除）就是教训：
跨模块外键会把两个模块焊死，谁也没法单独动。
存一个裸 uuid + source 字段即可，v1 只写 manual/import，
news/chat 两个值留给将来的跨模块转存。
```

==问题：为什么要冗余一个 `preview` 列？==

```file:5-4 结论：写入时算一次，读时零成本
星图一次要 200 条摘要：
(a) 读时 substr(content, 1, 80)：SQL 简单，但每读一次全表 text 都要过一遍；
(b) 写入时算好存 varchar(80)：读是纯定长列，且前端拿到的截断长度永远一致
    （不会这条 78 字那条 82 字）。
备忘录是"读远多于写"的典型，选 b。
附带收益：长文判定不用加接口字段——preview 以"…"结尾即代表正文超 80 字。
```

### 5.2 三个索引

```file:5-5 索引与查询路径的对应
ix_stars_user_id                      list_stars 的 base filter（user_id）
ix_stars_user_archived_created        (user_id, is_archived, created_at DESC)
                                      主查询 + 排序一步走完
ix_stars_tags_gin                     tags jsonb @> 的 GIN 索引，
                                      没有它会退化成全表扫描

注意：复合索引在模型 __table_args__ 里同步声明了一份。只在迁移里创建的话，
下次 alembic autogenerate 会认为它是"多余索引"并 drop 掉。
GIN 索引标准 Index 表达不了，只留在迁移里，注释中已标明需人工同步。
```

### 5.2 批量导入

```file:5-5b 跳过四种行，超长行不拒绝整批
① 纯空白行（粘贴时常带）
② 批次内重复
③ 与夜空中已有内容完全相同（用户重复粘贴同一段旧笔记时，
   不该凭空多出一把一模一样的星）
④ 超过单颗正文字符上限的

④ 用 skip 而不是 422 拒绝整批：一次粘贴两百行里混进一条超长的，
为它废掉整次导入太不值。这条决定与"捕获层零摩擦"是同一条原则。
```

### 5.3 前端：星图布局

**这是本模块唯一有技术风险的地方。**

==问题：星体位置按什么算？==

```file:5-6 结论：位置只由 id 决定，与列表构成完全解耦
反面做法：按列表序号黄金角向日葵排布（θ = i·137.5°, r = R·√((i+0.5)/N)）。
它分布均匀，但位置依赖 i——一筛选、一翻页、一归档，剩下的星全部换位，
用户刚建立的空间记忆瞬间归零。

正确做法（StarField.placeStar）：
  h1 = fnv1a(id)  →  t = (h1 >>> 8) / 0xFFFFFF        // 半径分量
  h2 = fnv1a(id+":twinkle")  →  θ = 2π·h2 / 0x100000000  // 角度
  x = cos(θ)·√t·RX      y = sin(θ)·√t·RY
  置顶星再乘 PIN_RATIO(0.45) 压到内圈

三条性质都是必需的：
- 稳定：筛选/分页/归档都不改变任何一颗星的位置，用户能建立"那颗在左上角"的记忆；
- 满覆盖：t 连续取自 hash，20 颗和 500 颗都铺满整个椭圆，不挤成一团；
- 零碰撞：连续值而非离散槽位，重复概率≈0（离散槽位 500 颗/4096 槽时期望约
  30 对重叠，重叠的两颗里有一颗点不到）。

√t 而不是 t：t 均匀分布时，√t 在圆盘上才均匀，否则星明显向圆心聚集。
```

==问题：DOM 还是 Canvas？==

```file:5-7 结论：DOM 元素 + CSS transform，200 颗封顶
DOM（≤200 颗）            每颗是真 <button>，键盘、a11y、事件全免费
Canvas（上万）            要自己做 hit-testing、focus 管理、屏幕阅读器支持，
                          约多 3-5 人天且不可逆

选 DOM。这是个人备忘录不是可视化大屏，为 1% 的极端数据量牺牲 100% 场景的
无障碍与可维护性不划算。上限的缺口用两条路补：
① 底部常驻"夜空中 N 颗 · 当前视野 M 颗"（如实告知，不静默截断）；
② "再望远处一些"追加一页，以及筛选/搜索。
```

==问题：闪烁动画怎么跑？==

```file:5-8 结论：纯 CSS，零 JS
@keyframes twinkle { 0%,100% { opacity:.55 } 50% { opacity:1 } }
每颗星的 animation-duration（2.6-4.9s）与 animation-delay（-3.9-0s）
由 id 哈希派生后写进 inline style，200 颗各自错峰。
- 合成层处理，主线程零开销，不跑 rAF 循环；
- 只动 opacity 不动 transform：星体自己在用 transform 做定位与 hover 缩放，
  两个 transform 动画会互相覆盖；
- 下限 0.55 而不是 0：完全暗下去的星会被当成"这颗没了"；
- prefers-reduced-motion 下由 index.css 文末的全局规则压成静止，
  星体变成常亮的点，语义不丢——新模块白拿站内既有的降级能力。
```

### 5.4 前端：抓取的 FLIP

```file:5-9 抽屉从星体位置飞出
点击时记下 e.currentTarget.getBoundingClientRect()，抽屉首帧把 transform
设成"从星体中心平移到抽屉中心 + 缩到 0.14-0.5"，下一帧清掉 transform，
浏览器补出 260ms 的 cubic-bezier(0.16,1,0.3,1) 过渡。

缩放系数：星点本身只有 3-5px，按真实比例算会缩到看不见；
按 originRect.width/panel.width × 4 并夹在 0.14-0.5，
读起来是"一颗光点绽开成一面星图"。

reduced-motion 下直接跳过，退化为淡入。约 25 行代码换一个动作的全部身体感。
```

### 5.5 交互细节取舍

```file:5-10 三处刻意的取舍
① 抽屉永远渲染在 DOM 里（无选中时显示引导语），好处是 xl 断点并排布局稳定；
   代价是小屏上会盖住夜空，故 idle 时在小屏 hidden、xl 仍 flex。
② 筛选一律即时生效并重置分页，没有"应用筛选"按钮——筛选是探索动作不是提交动作。
③ 顶栏输入框回车即收录（最短路径），旁边一支笔打开完整弹窗（多行+标签+收藏）。
   两个入口职责不同，不写成一个"写下一念"按钮让人猜。
```

==问题：搜索用 ilike 够吗？==

```file:5-11 结论：够，且 % 和 _ 已转义
_escape_like 把 \ % _ 三个字符转义后再拼 %q%，用户搜"100%"或"a_b"
按字面量匹配而不是通配符。个人量级（千行）远没到需要 pg_trgm 的阶段，
文档记下升级路径即可。
```

==问题：mark_grabbed 做在 GET 上，不脏吗？==

```file:5-12 结论：脏，但值得，且已留痕
每次打开详情多一条 UPDATE。收益是"抓"这个核心动词被记录了，
last_grabbed_at 能支撑将来的"最常回味的星"排序。
代价写进了代码注释：GET 不再纯净，将来要上缓存时这一行必须一起挪走。
配套：commit 后必须 db.refresh(star)——expire_on_commit=False 时
实例属性过期后不会自动重载，不 refresh 的话同一响应里的 updated_at 是旧值，
抽屉的"改于"永远慢一拍。
```

### 5.5 前端状态管理的三处防护

```file:5-12b 三个非做不可的防护（都是多请求并发下的正确性问题）
① 请求序号：loadPage 用 requestIdRef 记最新请求号，过期响应直接丢弃。
   不做的后果：连续改筛选时先发的请求后返回，用旧 items/total/page
   覆盖新状态；append 分支还会把同一页重复追加进列表。
② 乐观更新回滚要连 items 一起：只恢复抽屉的话，请求失败后台列表里的
   置顶/收藏状态是错的，要等下一次加载才被人发现。
③ 编辑保存用后端返回的 saved 覆盖本地：tags 会在服务端 normalize_tags
   （去重/截断/去空白），本地合并会留下未归一化的结果；
   updated_at 不更新的话"改于"要等重开抽屉才出现。

另一处一致性：星图与清单一视同仁——只在"还没有任何星可看"时才整片换成骨架。
若星图分支只判 loading，点"再望远处一些"会让已有星星先闪没一次，像数据丢了。
```

### 5.6 API

| 方法 | 路径 | 说明 |
|----|----|----|
| GET | `/stars` | 分页列表，**只回 preview**；tag/range/favorite/pinned/archived/q，page_size ≤ 200 |
| GET | `/stars/tags` | 标签 + 使用计数（筛选 chip） |
| GET | `/stars/export?fmt=md\|json` | 整片夜空打包下载（2026-10-03 新增） |
| POST | `/stars/random` | `{count}` 随机取 N 颗全文（伸手抓一把） |
| POST | `/stars/import` | `{lines, tags}` 批量导入，回报 created/skipped |
| GET | `/stars/{id}` | 全文详情，同时标记 last_grabbed_at |
| POST | `/stars` | 新建，201。接受可选 `source` / `origin_ref`（跨模块转存） |
| PATCH | `/stars/{id}` | 局部更新（内容/标签/置顶/收藏/归档） |
| DELETE | `/stars/{id}` | 204 |

注意路由顺序：`/tags`、`/export`、`/random`、`/import` 四个静态段必须声明在 `/{star_id}` 之前。

`/stars/export` 的响应要带 `Content-Disposition`，且中文文件名需 RFC 5987 编码
（`filename*=UTF-8''...`）——否则 Windows 上下载下来是乱码名。写法上是
`ascii` 兜底名 + `filename*` 双写，老浏览器只看前者。

### 5.7 键盘

```file:5-11b 快捷键与作用域
N        新建（打开完整编辑弹窗）
R        伸手抓一把
/        聚焦搜索框
1-5      全部 / 今天 / 本周 / 本月 / 更早
Esc      关闭抽屉（焦点在输入框时先让输入框失焦）
←→↑↓    在星体间按空间最近邻移动（StarField 内）
Enter    顶栏输入框收录

作用域规则（两道关卡）：
1. 焦点在 INPUT/TEXTAREA/contenteditable 时，只放行 Esc（失焦），
   其余快捷键一律不抢——不然打一半字夜空突然重排是很恐怖的体验；
2. 任一弹窗（编辑/导入/删除确认）打开时，整组快捷键直接摘掉监听。
   光靠第 1 关不够：Radix 有时把焦点放在「取消」按钮上，那不在检查范围里，
   此时按 N 会再叠一个编辑弹窗出来。
```

方向键最近邻算法（`findNearest`）：只往按下方向找（投影必须为正），
用「前进量 + 横向偏移 × 2.2」打分取最小。横向惩罚让按右键优先选同一行的星。

## 9. 上线前置：两个真实踩到的坑

> [!warning]- 坑一：NUL 字节导致后端无法启动
> `app/services/star_service.py` 里一个本该是 `%/\_` 的转义写法被写成了 NUL 字节
> （`0x00`）。Python 无法编译含 NUL 的源文件，`uvicorn app.main:app` 会在 import
> 阶段直接崩，而**前端一切正常**——页面能开、能渲染，只是每个接口都失败，
> 登录页显示"操作失败，请重试"，极容易被误判成账号或数据库问题。
>
> 定位方式（不依赖任何第三方库，也不需要 venv）：
> ```python
> data = open(path, 'rb').read()
> print(data.count(0), [i for i, b in enumerate(data) if b == 0])
> ```
> 修复用 `data.replace(b'%/\x00 ', b'%/\_ ')` 后重写文件。
>
> 教训：往源文件里写 `%/_`、`\_`、`\x` 这类转义文本时要当心。

> [!warning]- 坑二：`StarSort.REVISED` 拼写错误，只打掉列表一个接口
> `list_stars` 里写的是 `sort is StarSort.REVISED`，而枚举成员叫 `REVISITED`：
> ```
> AttributeError: type object 'StarSort' has no attribute 'REVISED'. Did you mean: 'REVISITED'?
> ```
> 两个细节放大了排查成本：
> 1. **它写在 `A if 条件 else B` 的"条件"里**，所以不管 `sort` 传 recent 还是
>    revisited 都会炸——看起来像"排序功能整体坏了"，实际与 sort 无关；
> 2. **只有 `list_stars` 引用它**。`POST /stars`、`GET /stars/{id}`、`/tags`、
>    `/random`、`/export` 全部正常，所以"能收录、能看详情、能导出，就是列表 500"。
>    这种"一半接口好一半坏"的形态最容易让人怀疑是筛选条件或分页的问题，
>    而真实原因只是一个名字拼错。
>
> 排查手法：用项目 venv 直接调 service 层，一步拿到完整堆栈——
> `E:\pySpace\anaconda\envs\learner\python.exe`（本项目 poetry venv 的实际位置）。
> 比在 HTTP 层猜快一个数量级。
>
> 教训：枚举成员名写错，编译器不会拦（运行期才炸）。凡是 `X if 条件 else Y`
> 这种把分支判断和分支内容写在一起的地方，条件里的属性名要格外当心。

> [!warning]- 坑三：`--reload` 没加载修改，症状与"没修好"完全一样
> 改完 `REVISED` → `REVISITED` 后，直接调 service 层正常、单测全过，但 HTTP 仍然 500。
> 原因是 worker 进程启动于 22:13:32，而文件改于 22:54:15——`--reload` 这次没触发重载。
>
> 判断方法（PowerShell）：
> ```powershell
> (Get-Item <文件>).LastWriteTime
> (Get-Process -Id <uvicorn worker pid>).StartTime
> ```
> 文件比进程新 = 修改还没生效，重启后端即可。
>
> 教训：改完代码验证时，如果"代码看着对了但行为没变"，先确认跑的是不是新代码。
> worker pid 可用 `Get-CimInstance Win32_Process -Filter "name='python.exe'"` 列出
> （里面有 `spawn_main ... --multiprocessing-fork` 的那条就是 reload worker）。
